## Activation and owner agreement

Checkout defaults disabled in both private DB configuration and server configuration. `private.partner_billing_configuration` has one row per environment; `private.partner_entitlement_runtime` determines the runtime. No authenticated/service role has raw access. Owner checkout API derives auth.uid and requires current persisted owner + active owner membership; operational Pro managers and Benefitsi admins cannot accept an owner's agreement. No Commerce provider is required.

Before checkout: explicit server release configuration, dedicated freshly created SaaS customer, catalog checkout-enabled pinned price/version, unarchived offer/plan, and complete terms. Required private terms: `version`, HTTPS `document_url`, SHA256 `document_hash`, nonempty `first_payment`, `cancellation`, `minimum_term`, `price_change`, `trial_start_rule` (`checkout_created` or `fixed_date`, the latter requires `trial_start_at`). Supported cancellation policy additionally requires explicit `cancellation_mode:period_end`, `minimum_term_months:0`. No values are seeded and these are supported technical options, **not agreed terms**. Missing/different policies fail closed. A future user answer requiring a minimum term/different cancellation needs implementation before activation. Terms acceptance stores immutable snapshot, authenticated actor, pinned offer and audit; Checkout redirect/metadata never supplies agreement or entitlement authority.

Founder start is fixed in the intent, with exact second precision and Berlin six-calendar-month end. A configured fixed start must already have begun, with >49 hours remaining (Stripe trial minimum). Future scheduled starts are unavailable, rather than granting early access. First payment is the accepted trial end; the commercial text must match this supported rule. Standard/paid addons charge through Checkout immediately; no introductory addon trial. No automatic price changes, promotions or lifetime guarantee are inferred. Renewals retain the accepted offer version; future offer changes require a separate implementation/acceptance path.

## Founder campaign

`admin_set_partner_founder_eligibility(partner,city,evidence,eligible)` requires authenticated Benefitsi admin, actual city reference and documentary evidence; its decision and actor are audited. The city must match deployment's verified Annweiler campaign city; the setter itself rejects a forged/different campaign city. Admin UI path: select the partner in Admin → Einstellungen → Tarif & Module → Founder-Zulassung · Annweiler. It displays the server-configured campaign city, current decision/evidence/date and accepted-admission status; the decision form requires a documentary reason. Missing campaign configuration displays a blocked explanation. The existing admin audit history includes this decision. The form calls updatePartnerPlan(founder_eligibility), which checks requireAdmin and invokes the authenticated setter. It does not accept an agreement or reserve a seat on the owner’s behalf. Owner-editable partners.city_id/address is irrelevant. A microsite/Pro subscription is not required.

Campaign advisory lock serializes reservations at ten total pending+accepted partners per environment. Accepted admission survives cancellation and blocks another Founder trial. Pending intent expires after one hour, but elapsed time alone never releases capacity. Provider reconciliation must prove the bound Checkout expired without a subscription, or exhaust the dedicated customer's Checkout list after the deadline to establish no session was created. It recovers lost create responses by matching persisted client_reference_id under the dedicated customer. Customer mapping must exist before reserving, so directly calling the owner RPC cannot strand slots without a recoverable customer. After the fixed expires_at, Stripe cannot accept a new Checkout with that old expires_at. Accepted contracts cannot use the expiry path. Retry returns the same intent/session; Founder admission is never a concurrency-only cap.

## Authoritative processing

A private partner/environment lease is acquired before subscription/invoice/charge reads; monotonic fences plus a two-minute lease reject timed-out workers after another instance takes over. All webhook, reconcile and owner provider operations share this lock. Event identity is environment+ID+fingerprint, with immutable partner mapping, attempt count and sanitized failure code. SQL `batch` atomically commits all subscription/addon transitions, event completion and audit; thrown validation rolls the whole batch back. Failure recording/retry is separate. Duplicate event identity does not add quota or transitions; event-created order is not used as state truth.

Provider snapshot uses installed Stripe22.3.2 / `2026-06-24.dahlia`, item-level periods, invoice parent.subscription_details and paginated line/payment relationships. A known single licensed monthly item, quantity1, pinned exact EUR amount/tax/environment/customer, paid invoice and successful unrefunded/undisputed charge establish active rights. Active flag, zero/manual/out-of-band invoice, browser return, metadata or unknown price never grants Pro. Existing pinned deactivated Stripe prices are allowed for an existing contract, new checkout requires active price. Unknown items, discounts, pause_collection and subscription schedules fail closed for review. Trials require exact accepted Founder trial end. Reconciliation reads the latest contract per base/addon family; old subscription events cannot overwrite its successor.

Refund or dispute on the current paid invoice yields unpaid; historical events cause a new authoritative current-state evaluation rather than blindly revoking a later paid period. Any partial refund is conservatively unpaid pending review. No automatic refunds/credits are issued. A valid subsequent payment/current active state recovers rights. Initial incomplete/expired unacknowledged trial never gets grace. For a previously paid continuing period, first failure uses provider invoice finalization time (bounded by current time), subsequent failures retain the same DB past_due_since. Old disconnected paid-through cannot create a fresh episode. Only valid active payment clears it; central resolver expires seven days exactly, independently of job delivery. Records, earned rewards, orders and existing data are not deleted by downgrade; existing quota triggers block new over-limit activation without randomly suspending staff.

## Modules and Portal

Separate subscription per addon, within one dedicated SaaS customer per partner/environment. Customer IDs are unique and checked against known legacy Commerce/Consumer mappings. Before Portal (and checkout reuse), provider pagination checks **all** customer subscriptions and invoices against persisted contracts; metadata alone cannot authorize Portal. Explicit inspected portal configuration must match environment, be active, enable invoices/payment-method updates and disable subscription updates **and cancellation**. Never use the account default. Direct owner base/module cancel actions remain functional without subscription schedules. An individual module stops at its own period end without changing paid Pro. Base cancellation stops addon renewal no later than the earlier of addon paid period end and base end. A verified terminal/expired base cancels remaining addon subscriptions without new invoice/proration; no refund policy is invented. API errors remain retryable failures.

Addon checkout requires valid active/trial Pro, no pending Pro cancellation, and central readiness. During Founder trial, it bills immediately with explicit prorations to the next **monthly** original-anchor anniversary; it never uses the six-month trial end as a distant addon billing anchor. The amount appears in Stripe Checkout before the final confirmation. Later monthly addon periods come from Stripe. Task6 must also enforce the central Pro prerequisite for new module use; scanner/authorized existing-order completion must remain independent. Successful cancellation does not delete paid work/orders. Potential provider outage still requires scheduled reconciliation before renewal deadlines: release must configure and monitor the job.
