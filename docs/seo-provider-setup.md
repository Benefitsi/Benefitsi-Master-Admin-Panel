# SEO provider preparation and Google measurements

`/seo` is restricted by the existing admin authorization. Choose a target before editing its public profile packet or requesting a measurement. Partner self-service stays closed until a target ownership/RLS contract is implemented and reviewed. This preparation does not change publication, prelaunch/noindex, editorial approvals, target status, existing provider settings, or measurement readiness. There are no external listing writes, subscriptions, paid-provider purchases, or scheduled jobs.

## Public profile packet

Profile setup is available only for domain and partner microsite targets. City and editorial targets are pages, not independent businesses: the form is hidden and the server rejects setup saves for those types, while Google measurements remain available.

The panel stores only bounded public company name, address, phone, description, website, supported profile URLs, and explicit manual confirmations under `seo_targets.provider_config.setup`. The other provider settings remain intact. Saving uses the target's `updated_at` as an optimistic concurrency condition and verifies that one row was affected; reload on a stale-save error. A download contains only the saved public setup fields and canonical URL, never environment credentials or the rest of provider_config. Unsaved edits are not included.

Use the official onboarding links in the panel: [Google Business Profile](https://www.google.com/business/), [Apple Business](https://business.apple.com/), [Bing Places](https://www.bing.com/forbusiness/), [Yelp](https://biz.yelp.de/), and [Gelbe Seiten](https://www.gelbeseiten.de/). Check each provider's eligibility before claiming a profile. Google requires qualifying in-person customer contact; a website alone does not establish eligibility. Only select “manually checked” after confirming public business information, ownership, eligibility, and the public profile URL. For Apple agency use, organisation verification and partner API access/integration review are separate approvals; each customer must subsequently delegate its brand or locations. See [agency registration](https://support.apple.com/guide/business/register-your-third-party-partner-or-agency-abcbec357512/web), [partner API access](https://support.apple.com/guide/business/apple-business-partner-api-access-abcb4226f877/web), and [delegation](https://support.apple.com/guide/business/share-access-with-a-third-party-partner-abcb3f4a4f2f/web). These confirmations are human declarations, not automatic sync or provider verification. Avoid advertising/paid upgrades. ProvenExpert is not part of this setup.

## Server credentials

Set these only in the server environment or private `.env.local`. Never use `NEXT_PUBLIC_`, the profile form, git, screenshots, or job payloads for credentials. `.env.example` leaves every new value empty.

1. In a Google Cloud project controlled by Benefitsi, enable Search Console API. Configure the OAuth consent screen and an OAuth client; put its client ID and secret in `SEO_GOOGLE_CLIENT_ID` and `SEO_GOOGLE_CLIENT_SECRET`. Use the exact authorized redirect URI of your trusted OAuth flow.
2. Authorize an account that has read access to the verified Benefitsi Search Console property, requesting **only** `https://www.googleapis.com/auth/webmasters.readonly`, with offline access and consent to obtain a refresh token. Store that token in `SEO_GOOGLE_REFRESH_TOKEN`. Do not authorize the broader `webmasters` write scope. A refresh token issued with broader scopes must be revoked and replaced; the refresh request here does not substitute for checking original consent.
3. Set `SEO_GSC_PROPERTY` to the exact verified property identifier. For the currently verified URL-prefix property this is `https://benefitsi.de/`. `sc-domain:benefitsi.de` is accepted only if that domain property has separately been verified and granted to the account. Other properties are rejected. The verification of the property itself does not configure application OAuth credentials.
4. Enable PageSpeed Insights API in an approved Google Cloud project. Create a server API key restricted to that API (and approved server IPs if applicable), store it in `SEO_PAGESPEED_API_KEY`, and set appropriate quota limits. Do not enable billing, buy quota, or enable a paid provider to make a test pass. Missing key means unconfigured, with no anonymous fallback request.
5. Keep refresh tokens and keys in the approved server secret store. Revoke/rotate compromised or unused credentials. A revoked grant or 401 requires reauthorization; 403 requires access/API checks; 429 requires waiting or reducing usage, never automatic quota purchase.

As of the initial preparation, the own Search Console property is verified and associated with Analytics, but the five app credential variables have not been provisioned. Manual profile ownership/eligibility and publication/indexing approvals remain outstanding until the administrator records them. Existing paused partner targets are not activated by this feature.

## Measurements and evidence

[Search Analytics documentation](https://developers.google.com/webmaster-tools/v1/searchanalytics/query): each run queries totals separately from up to 25 top query rows, for 28 inclusive finalized days ending three days before the current Pacific date. GSC dates use `America/Los_Angeles`. Query rows can exclude anonymized queries, so they must not be summed to infer totals. Average position is Google's aggregated search-result position, not a keyword rank tracker. Empty rows mean no data; actual numeric zero is retained only if returned by Google.

Only HTTPS URLs on the exact `benefitsi.de` host are accepted. Only a root domain target with both `partner_id` and `city_id` null can read property-wide totals. Every other target—including partner, city, editorial and non-root domain targets—uses `page equals <canonical URL>` on both queries. The canonical URL is read from the database after admin authorization, never from hidden input.

[PageSpeed documentation](https://developers.google.com/speed/docs/insights/v5/get-started): each explicit request uses mobile Lighthouse laboratory measurements. Missing categories and metrics remain null, and partial data is labelled partial. These are lab results, not Core Web Vitals field data or organic rankings. The returned final URL must belong to Benefitsi and match the requested canonical path; redirects to another page are rejected. Requests have timeouts, no automatic retries, no HTTP redirect following, and a 5 MB response limit.

Every attempted provider read produces an audit with methodology `benefitsi-google-measurement-v1`, target, source, observation time, structured evidence, and bounded state (`ok`, `partial`, `no_data`, `unconfigured`, `auth_error`, `forbidden`, `rate_limited`, `timeout`, `invalid_target`, `invalid_response`, `provider_error`). Failed and unavailable reads are persisted honestly. Scores are always `{}`; this never creates score snapshots or modifies composite rankings. Zero coverage denotes unavailable evidence, not a zero provider measurement. Existing audit/rank buttons retain their behavior.

## Required live readback before scheduling

After credentials and permissions are manually provisioned, an administrator must run one GSC and one PSI check on an approved own target, inspect the saved target-scoped audit evidence, compare GSC period/totals to Search Console and PSI lab values to the official report, and confirm that no raw credentials entered the evidence. Repeat a GSC check on an approved city/partner URL and verify the exact page scope. Record timestamp, target, audit ID, result state, and reviewer in the operational handoff. Do not mark readiness or enable scheduling from setup completion, property verification, or fixture tests alone. Scheduling needs a separately approved cadence/quota policy and successful live readback. Prelaunch/noindex remains until explicit publication approval.
